# Test Design Review

Decide whether the affected coverage protects the right claim. A code change does not require a new test. An existing expectation does not deserve to be kept or updated automatically.

Find the project's testing policy through the nearest `AGENTS.md` or contributor guide. It overrides this skill. Do not restate it.

## Questions

- **Claim.** What observable behavior, regression, contract, or invariant does the test protect? Without an independent claim, the test records the implementation instead of constraining it.
- **Oracle.** Where does the expected value come from? An accepted contract, reviewed evidence, or an established reference counts. Output generated by the code under test does not. Hard-coded counts, versions, and inventories are valid only when that exact value is the contract.
- **Existing coverage.** Which nearby test already protects this? Which distinct, plausible failure would this test catch? Duplicates add upkeep without confidence.
- **Stability.** Would the assertion survive a correct internal rewrite? Private structure, helper calls, incidental formatting, and mutable inventories are unstable unless a contract exposes them.
- **Layer and cost.** Is this the smallest useful layer and input? Fixtures, snapshots, and test-only APIs are maintained code. Do not distort production design to expose internals.
- **Ownership.** Name the stable feature that owns the test. Organize by feature and behavior, not by Issue, PR, or task ID. An ID may appear only as related history.

Why: a test should fail when behavior is wrong and stay green through a correct refactor. A test edited only to restore green CI usually fails the first property.

## Decision

Return one recommendation:

- `keep`: protects a durable claim or distinct failure mode at reasonable cost.
- `consolidate`: the coverage is valuable but can be merged or moved to a better surface.
- `rewrite`: the claim is valuable, but the assertions, input, or boundary target unstable behavior.
- `delete`: no durable claim or distinct failure mode. It mirrors the implementation.

```text
Recommendation: keep | consolidate | rewrite | delete
Feature: <stable owning feature>
Claim: <behavior, regression, or invariant>
Rationale: <why it does or does not add durable protection>
Existing coverage: <overlap or distinct failure mode>
Cost/coupling: <material concern, if any>
```

Do not manufacture a test because code changed. Whether a fixture or snapshot belongs in the repo is decided by the project's testing policy.
